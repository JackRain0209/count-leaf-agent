# VLM 批量识别失败与耗时问题修复记录

- 日期：2026-09-19
- 分支：`debug`
- 范围：`app/` 下的 VLM 调用与中断处理；不含 CV 算法改动
- 对应需求：`REQUIREMENTS.md` 的 R1（提高批量识别成功率）、R2（缩短识别耗时）

## 一、问题现象

1. 批量识别成功率极低：一批 25 张只有 3 张成功（约 12%）。
2. 单张识别耗时极长，经常长时间卡住不动，用户只能手动停止。

## 二、排查方式

排查前没有任何可用的现场数据（`history.sqlite3` 为空，失败批次的数据在另一台机器上），
且失败原因在代码里被压成一句话，无法区分。因此先补了埋点再复现。

新增 `app/trace.py`，把 pipeline 的真实行为写成 JSONL（`results/_trace/trace.jsonl`）：

- 每次 VLM 调用：阶段名、耗时、prompt/completion/reasoning token、异常类型与 HTTP 状态
- 每个阶段：墙钟耗时
- 每张图：开始/结束、状态、失败原因分类

埋点是纯增量的，不改变任何控制流和返回值。

## 三、定位到的四个原因

### 1. 账号级限流（外部原因，非代码）

埋点抓到接口返回的原文：

```
RateLimitError  429
Your account [2122781975] has reached the set inference limit for the
[doubao-seed-2-1-turbo] model, and the model service has been paused.
```

账号达到推理额度上限后模型被暂停，此后**所有**调用都会立即返回 429。
这解释了"前几张成功、后面全失败"的模式：额度在批次中途耗尽。

**处理**：在火山方舟控制台关闭 `doubao-seed-2-1-turbo` 的"安全体验模式"。非代码改动。

### 2. 错误信息被当成数据解析（代码 bug，掩盖了真因）

`vlm_counter.py` 捕获 API 异常后，把异常压成一个字符串：

```python
raw_response = f"Doubao API error: {e}"
```

而上面那条 429 报错原文里带有方括号 `[2122781975]`、`[doubao-seed-2-1-turbo]`，
于是被 `_extract_json_array` 当成 JSON 数组提取出来：

```
'[2122781975]'  →  _parse_json  →  plants = [2122781975]
```

`plants` 因此非空（是个 list），**绕过了下游 `if not plants` 的空值守卫**，
继续走到 `for p in plants: p.get("bbox")` 时对 int 调用 `.get()`：

```
AttributeError: 'int' object has no attribute 'get'
```

**后果**：真实的 429 限流被伪装成一个莫名的 AttributeError，
数据库里存的也是这句话，排查时完全看不出是限流。

### 3. 思考模式（耗时主因）

当前 endpoint 映射到 `doubao-seed-2-1-turbo`，是带思考能力的多模态模型，默认开启思考。

实测数据：

| 场景 | 耗时 | reasoning token |
| --- | --- | --- |
| 思考开启（默认） | 281s，且实测出现 1118s / 1202s | 3674 ~ 32364 |
| `thinking={"type":"disabled"}` | 2.9s | 0 |
| `reasoning_effort="minimal"` | 1.9s | 0 |

单张图的 VLM 调用拿到过 **99.4% 的输出 token 是 reasoning**（142,596 / 143,443）。
思考长度还极不稳定，同一张图同一 prompt 会出现 3334 与 5245 的差异。

### 4. 无超时 + 静默重试

`_get_client()` 没有配置超时和重试，沿用 openai SDK 默认值：

```
read timeout  = 600s
max_retries   = 2
```

read timeout 是"单次读取"超时而非总耗时超时，叠加自动重试后，
**一次调用最坏要 600 × 3 = 1800 秒（30 分钟）才失败**，且重试过程在日志里完全不可见。
实测出现过单次调用 1202.7 秒后才报错。

## 四、修复清单

| # | 内容 | 位置 |
| --- | --- | --- |
| 1 | API 失败时直接返回，不再尝试解析错误信息，并带出异常类型/HTTP 状态 | `vlm_counter.py` |
| 2 | 过滤掉 `plants` 里的非字典元素，防止模型返回 `[1,2,3]` 这类数组时崩溃 | `vlm_counter.py` |
| 3 | 失败信息透出真实原因（限流显示为限流，不再是笼统的"没识别到结构"） | `analyzer.py` |
| 4 | 新增 `VLM_THINKING` 开关，默认 `disabled` | `config.py` / `.env.example` |
| 5 | 新增 `VLM_TIMEOUT_S=120`、`VLM_MAX_RETRIES=1` | `config.py` / `.env.example` |
| 6 | 中断处理：阶段边界检查取消标记 + `finally` 兜底终态 + 启动时清理残留记录 | `cancel.py` / `analyzer.py` / `main.py` / `history.py` |
| 7 | 诊断埋点 | `trace.py` |

配置项（写在 `.env`，不提交）：

```
VLM_THINKING=disabled      # 改成 default 可切回思考开启
VLM_TIMEOUT_S=120
VLM_MAX_RETRIES=1
```

### 关于中断处理

实测（用假 pipeline 做真实断连实验）：客户端断开后同步生成器会被"抛弃"而不是"关闭"，
`finally` 要等到生成器被 GC 回收才执行，时机不确定；服务重启则完全不会执行。
另外断开后 pipeline 还会多跑一个阶段。

因此做了三层：阶段边界检查取消标记（挡掉多跑的那一个阶段）、`finally` 兜底终态、
启动时扫描残留的 `processing` 记录。

**已知未解决**：已经发出的那一次阻塞式 HTTP 请求无法中止，只能靠 `VLM_TIMEOUT_S` 兜住。
即点停止后仍可能多消耗一次调用的额度。

## 五、修复效果

### 耗时

三张图的实测（思考关闭后）：

| 图片 | 部件数 | 分枝数 | 角果数 | VLM 标注 | 裁剪复核 | CV 角果计数 | 总耗时 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| DJI_...0863 | 18 | 16 | 972 | 20.0s | 18.7s | **583.2s** | 653.8s |
| DJI_...0874 | 9 | 7 | 252 | 12.7s | 17.0s | 10.8s | 55.7s |
| DJI_...0880 | 6 | 4 | 239 | 8.8s | 6.8s | 6.5s | 40.0s |

- VLM 标注从"几百秒甚至跑不完"降到 **8.8 ~ 20 秒**
- 并行阶段（裁剪复核、角果复核）虽然各有十几次调用，墙钟只要 7 ~ 19 秒
- 三张图全部 `status=completed`

### 瓶颈转移

VLM 已不再是瓶颈。0863 那张图 **89% 的时间（583s）花在 CV 角果计数**上。

而且 CV 耗时是**超线性**的，不是随分枝数线性增长：

| 图片 | 分枝数 | 每分枝平均耗时 |
| --- | --- | --- |
| 0880 | 4 | 1.6s |
| 0874 | 7 | 1.5s |
| 0863 | 16 | **36.5s** |

角果密度几乎相同（每分枝 60 个 vs 61 个），耗时却差约 23 倍，
怀疑与裁剪图尺寸 / 骨架复杂度有关。**此方向尚未验证，属待查问题。**

## 六、精度说明（重要，尚未验证）

**思考关闭后，模型输出的结果与原配置不同。** 举例：同一张图同一个问题，
思考开启答 `8`、思考关闭答 `9`；部件识别数量也有变化。

目前只能确认：

- 输出**结构是合法的**——实测 13 个部件的 bbox 全部为规范的 4 元数值数组
- 三张图的流水线都能完整跑通

**不能确认的是识别精度有没有下降。** 仓库内没有真值表，无从比对。

**因此 `VLM_THINKING` 最终该取什么值，需要拿真值与 `default` 档做一次对比才能定。**
在拿到对比结论前，不应把"关掉思考"当作既定的最终方案。

## 七、遗留问题

1. **CV 角果计数耗时**：0863 高达 583s，且随图片复杂度超线性增长。现已成为主要瓶颈。
2. **已发出的请求无法中止**：点停止后仍可能多消耗一次调用额度（受 120s 超时约束）。
3. **精度未验证**：见第六节。
4. **思考长度不稳定**：即便保留思考，同一输入的耗时会大幅波动，难以预估。
