# 油菜考种工作台 · CV Agent

> **西南大学 · 谷昊林 · 个人作品**
>
> 一个**零训练数据、零标注成本**的油菜植株表型分析系统。
> 上传一张考种照片，自动完成「部件识别 → 角果计数 → 主干测量 → 人工复核」全流程。

---

## 一句话概括

**科研人员考种时要人工数角果——单株 10 分钟，主观误差大，几万张照片根本数不完。**

本系统用 **VLM + 传统 CV 协同**的方案，把这件事自动化：**不采集标注数据、不训练模型**，直接调用通用视觉模型完成识别，再用经典图像算法做精确计数。

---

## 核心亮点

### ① 零训练数据 —— 这是整个方案最关键的设计决策

**常规做法走不通**：科研团队有几万张照片，但**没有标注**；重新标注的成本远超项目经费；从头训练模型的算力开销也承担不起。

**我们的方案**：不做训练，改用 **few-shot 结构化 Prompt 驱动通用视觉模型**完成语义理解（它认识主干、主枝、分枝长什么样），再交给**传统 CV 算法**做像素级精确计数。

> **一句话**：让 VLM 干「理解」的活，让 CV 干「数数」的活。两者各司其职，绕开了数据依赖。

**这带来的好处**：
- **零标注成本** —— 不需要人工标一张图
- **零训练成本** —— 不需要 GPU、不需要训练周期
- **可迁移** —— 换一个作物（比如大豆、小麦），改 Prompt 即可，不用重新训模型

### ② 对复杂场景的鲁棒性

真实考种照片的问题五花八门，单一算法必然失效。系统用三个机制兜住：

| 问题 | 应对 |
|---|---|
| **部件裁剪不准**（VLM 框偏了） | **VLM 裁剪二次验证** —— 把「原图 + 裁剪图」一起发给模型，判断 keep / delete / recrop，自动重截 |
| **枯枝被误判成角果** | **VLM 正反例复核** —— 用预先收集的枯枝正反例图，让模型只剔除 false positive |
| **尖端粘连导致漏数** | **果柄法**替代骨架法 —— 从「数线段」改为「找果柄连接点」，绕开粘连 |

**而且这套流程是自洽的**：每一步的错误都会被下一步兜住，不会级联放大。

### ③ 工程化程度

| 能力 | 说明 |
|---|---|
| **7 阶段可视化流水线** | SSE 实时推送每一步（含中间步骤图），出问题能定位到具体环节 |
| **CV-only 快速复跑** | 首次 VLM 标注后持久化裁剪图与元数据，后续调算法参数**跳过 VLM**批量复跑，省时省钱 |
| **人工复核闭环** | 支持修改部件、增删分枝、恢复原始结果；修改后自动重算 |
| **完整留痕** | 保存中间步骤图、VLM 原始响应、验证裁剪，便于复核与追溯 |

## 效果数据

**测试集**：15 个真实考种样本（含多分枝、高密度角果的复杂样本）

| 指标 | 结果 |
|---|---|
| **单株总角果准确率** | **平均 86.9%**，中位数 90.0%，**最优 97.7%** |
| **分枝数识别准确率** | **100%**（15/15 全部识别正确） |
| **主花序准确率** | 平均 87.4% |
| 对比：旧方案（骨架/图论法） | 平均约 72% |

> **从 72% → 86.9%，靠的是换方法（果柄法 + VLM 复核），不是加数据。**

各样本明细：

```
95.1%  97.3%  97.5%  93.5%  93.2%
71.0%  88.7%  88.3%  64.7%  85.3%
90.0%  94.4%  97.7%  61.8%  84.9%
```

## ⚠️ 适用边界（重要）

**这套系统是为「科研级、标准化拍摄的考种照片」设计的，不是通用农产品识别工具。** 使用前请确认输入符合以下条件：

### 输入照片要求

- ✅ **纯色背景布**（现用黑色），避免背景干扰
- ✅ **画面左侧放置已知长度的标尺**（用于长度换算）
- ✅ **植株平铺展开**，减少分枝重叠
- ✅ **俯拍，光线均匀**，避免阴影
- ✅ **主干、主枝、分枝末端完整入镜**

### 已知限制

| 限制 | 说明 |
|---|---|
| **同株分枝不可严重重叠** | 交叉遮挡会导致漏数。当前粘连检测模块处于停用状态，严重重叠样本准确率会明显下降 |
| **异株不可粘连** | 系统默认「一张图一株」，无法自动分割交叉生长的多株植株 |
| **角果尖端粘连仍是主要误差源** | 高密度样本（如 396 果）误差可达 58 个，是当前 P0 待优化项 |
| **依赖标准化拍摄** | 手机随手拍、背景杂乱、光照不均的照片不在适用范围内 |

> **为什么要把限制写清楚**：这个系统是为了替代**重复劳动**，不是替代**科研判断**。系统输出的是「初筛结果 + 可复核的中间证据」，最终数据仍需研究人员确认。
>
> **给出准确的边界，比给出漂亮的数字更有价值。**

## 技术方案

### 处理流水线（7 阶段）

```text
① 原始图片加载
       ↓
② VLM 部件识别        —— 识别主干 / 主枝 / 分枝，返回归一化 bbox
       ↓
③ VLM 裁剪验证（并行） —— keep / delete / recrop，剔除无效裁剪
       ↓
④ 缓存已验证裁剪       —— 供后续 CV-only 模式复用，跳过 VLM
       ↓
⑤ CV 角果计数          —— 果柄法：二值化 → 骨架化 → 拓扑计数
       ↓
⑥ VLM 角果复核（并行） —— 用枯枝正反例图剔除误报
       ↓
⑦ 汇总输出             —— 部件明细、角果汇总、主干长度、步骤图
```

### 技术栈

| 层 | 技术 |
|---|---|
| **后端** | Python · FastAPI · Uvicorn · **SSE 流式推送** |
| **前端** | 原生 JS 单页应用（无框架），暗色主题 |
| **VLM** | 豆包 Vision（Ark API） |
| **CV** | OpenCV · scikit-image（骨架化）· **Numba（BFS 加速）** · PlantCV |
| **存储** | SQLite（识别历史 + 人工修订） |
| **部署** | Docker Compose，单用户本机服务 |

### 代码规模

```
后端流水线    ~4,500 行 Python
前端单页      ~1,500 行（原生 JS）
```

## 快速开始

### Docker（推荐）

```bash
cp .env.example .env
# 编辑 .env，填入 ARK_API_KEY / VLM_MODEL
docker compose up -d --build
```

打开 `http://localhost:8501`

### 本地开发

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python -m app.main
```

### API

分析接口返回 `text/event-stream`，逐行推送 `data: {JSON}`。

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/analyze` | 上传图片并启动分析 |
| `POST` | `/api/analyze_online` | 分析数据目录下的图片 |
| `GET` | `/api/history` | 查询历史记录（支持分页与搜索） |
| `PUT` | `/api/history/{run_id}` | 保存人工修改 |
| `POST` | `/api/history/{run_id}/restore` | 恢复原始识别结果 |
| `GET` | `/api/health` | 健康检查 |

## 迭代过程（这个项目最有价值的部分）

| 阶段 | 方案 | 准确率 | 问题 |
|---|---|---|---|
| v1 | 骨架遍历法 | ~73% | 角果粘连就漏数 |
| v2 | 拓扑图法 | ~72% | 同上，且参数敏感 |
| **v3** | **果柄法 + VLM 复核** | **86.9%** | 疑难样本仍有误差 |

**最大的教训**：一开始我在优化「怎么把角果数准」——试了 4 套算法，收益都很有限。

**后来想通了**：这个问题的本质不是「算法不够好」，而是**「我没有可用的训练数据，却想让它达到有监督模型的精度」**。

**所以换了思路**：不去硬追求单点精度的极限，而是**用 VLM 补上语义理解、用 CV 补上像素精度、用人工复核兜住剩余误差**——把一个「追求 100% 自动」的问题，改造成「追求 90% 自动 + 10% 可高效复核」。

**这个转变，比任何一个算法优化带来的提升都大。**
